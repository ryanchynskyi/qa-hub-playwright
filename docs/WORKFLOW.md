# Workflow фреймворку

Як фреймворк запускається, як він живе в CI і як його розвивають агенти. Кожен крок має «чому»:
саме це питають на співбесіді.

```
            ┌──────────── агенти (Claude Code) ────────────┐
 нова фіча  │ planner → specs/*.md → generator → tests/*   │
 червоний   │ healer → виправлений тест                    │
            │            ↓                                 │
            │ test-reviewer (правила фреймворку) → commit  │
            └──────────────────────┬───────────────────────┘
                                   ↓ push / PR / nightly / app-updated
                          GitHub Actions (e2e.yml)
          check → локальна копія апки + Postgres → playwright test → HTML-звіт
```

## 1. Локальний запуск: що відбувається після `npm test`

1. **`playwright.config.ts`** читає `src/config/env.ts`: ціль (`TARGET=local|prod`) і URL.
   Віддалений URL без `TARGET=prod` зупиняє запуск ще на старті конфігу.
   *Чому:* одна помилка в env-змінній не може відправити повний набір (з реєстрацією і
   видаленням акаунтів) на прод.
2. **`webServer`** запускає `scripts/stack.mjs`, якщо стек ще не працює. Це Postgres
   (окрема БД `qahub_pw`), API апки на :3200 і зібраний web на :4273. Тести ходять в API
   через проксі web-сервера (`:4273/api/`).
   *Чому:* тестуємо справжню апку, а не моки, і на своїй БД, тому тести можна сміливо скидати.
   Проксі потрібен, щоб refresh-cookie після API-логіну потрапила на origin сторінки.
3. **`globalSetup`** чекає `/health` з `db: up`.
   *Чому:* якщо API чи БД лежить, запуск падає один раз із причиною, а не кожен тест окремо.
   Таймаут 30 с: прод на тарифі Render без сну (REQ-NFR-09), чекати холодного старту не треба.
4. **Проєкти:**
   - `api`;
   - `desktop`: усі UI-тести;
   - `tablet` і `phone`: тільки `@responsive`.

   *Чому:* layout перевіряємо на всіх трьох в'юпортах, а бізнес-логіку один раз, бо вона від
   ширини екрана не залежить.
5. **Фікстури** (`src/fixtures`) готують кожен тест:
   - `context` ще до старту апки пише в localStorage, що аналітика вимкнена, focus wizard
     пропущено (`qa-hub-focus=skipped`), тур пройдено, і яка мова;
   - `user` створює акаунт через API і видаляє його після тесту; з `TARGET=prod` вона (як і
     `newCredentials`) кидає помилку;
   - `authedPage` логіниться через API, без UI.

   *Чому:* кожен тест незалежний, тому `fullyParallel` безпечний. UI-логін тестується тільки
   в `auth.spec.ts`, а не в кожному тесті.

## 2. Шари коду

| Шар | Що робить | Правило |
|---|---|---|
| `src/api` | `ApiClient` + zod-схеми | типізовані методи перевіряють статус і контракт; `raw` для негативних тестів |
| `src/pages`, `src/components/shell.ts` | page objects | тільки `data-testid` / `data-key`, без тексту (UI двомовний) |
| `src/fixtures` | збирає все для тесту | спеки імпортують `test` звідси, не з `@playwright/test` |
| `tests/` | сценарії | без `if (device)`: різницю між пристроями ховає `Shell` |

**Трасування вимог.** Кожен тест, що перевіряє вимогу, має тег `@REQ-<розділ>-<nn>` з [specs/COVERAGE.md](../specs/COVERAGE.md).
`npm run coverage` показує «вимога → тести» з `playwright test --list` і падає, якщо матриця
бреше: ✅/🟡 без жодного тесту, ❌ з тестом, тег неіснуючої вимоги. `npx playwright test --grep
@REQ-AUTH` запускає розділ. Тести без тегу (інфраструктурні: health, каталог) скрипт лише перелічує.
*Чому теги, а не таблиця вручну:* таблицю забувають оновити, а тег живе поруч із тестом, і CI
перевіряє, що вони сходяться. Статус ✅ чи 🟡 лишається рішенням людини: скрипт не знає, чи тест
перевіряє вимогу повністю.

**Guard для test id.** `npm run check:ids` звіряє кожен `getByTestId` / `byTestId` /
`data-testid` у `src/` і `tests/` з каталогом апки.
*Чому:* апка перейменовує чи прибирає id незалежно від фреймворку. Guard падає за секунду з
назвою id, а не через 30 с таймауту локатора в кожному тесті.

Ці правила перевіряє `test-reviewer` ([.claude/agents/test-reviewer.md](../.claude/agents/test-reviewer.md)).

## 3. CI (`.github/workflows/e2e.yml`)

**Тригери:**

| Тригер | Навіщо |
|---|---|
| push у `main`, pull request | не пустити зламаний фреймворк |
| `schedule` щоночі о 04:00 UTC | апка змінюється незалежно від фреймворку; вранці вже видно, що зламалось |
| `repository_dispatch: app-updated` | апка після деплою сама запускає тести |
| `workflow_dispatch` | ручний запуск, input `app_ref` (гілка, тег чи SHA апки, за замовчуванням `main`) |

**Кроки job `e2e`:**
1. checkout фреймворку і апки (приватне репо, токен `APP_REPO_TOKEN`); SHA апки йде в summary
   прогону, щоб було видно, проти якої версії апки він ішов;
2. Postgres як service;
3. `npm run check`: types, lint, format, `check:ids` (кожен test id фреймворку є в
   `$APP_DIR/docs/test-ids.md` апки) і `coverage` (теги `@REQ-*` сходяться з матрицею в
   `specs/COVERAGE.md`);
4. браузер: Chromium з кешу за версією `@playwright/test`, системні бібліотеки ставляться завжди;
5. `playwright test` (той самий `webServer` піднімає стек);
6. HTML-звіт як артефакт на 14 днів.

**Branch protection на `main`:** PR зливається лише з зеленим `e2e`, правило діє й на адміна,
прямий push у `main` заборонено. Code review не обов'язковий: фреймворк веде одна людина, а
перевірку правил робить `test-reviewer`.
*Чому і для адміна:* інакше правило лише попереджає, а червоний PR «один раз» зливають саме тоді,
коли поспішають.

*Чому `concurrency`:* новий push у PR скасовує старий прогін того ж PR, бо його результат уже
нікому не потрібен. Прогони на `main` (push, nightly) не скасовуються: їхня історія і є
сигналом, коли щось зламалось.

*Чому один job, а не `gate` + `full`:* увесь набір іде ~1,5 хв, окремий швидкий gate нічого не
виграє. Ділимо і шардимо (`--shard` + `merge-reports`), коли набір перевалить за ~10 хв.

**Workflow `prod-smoke`** (`.github/workflows/prod-smoke.yml`): `TARGET=prod`, лише
`@prod-safe` (read-only), без копії апки і без секретів, `--workers=2`, timeout 10 хв.
Тригери: cron `17 */3 * * *`, `repository_dispatch: prod-deployed` (апка після деплою) і ручний.
Падіння відкриває issue «Prod smoke failing» або коментує вже відкрите; перший зелений прогін
його закриває (`scripts/prod-alert.sh`, `permissions: issues: write`). Звіт зберігається лише
при падінні. Відкрите issue скрипт шукає в повному списку, а не через `--search`: пошуковий
індекс GitHub відстає, і на пробному прогоні два збої поспіль відкрили два issue (#9, #10).
*Чому окремий workflow:* у нього свій розклад, свої права (`issues: write`) і своя черга
(`concurrency: prod-smoke` без скасування: прогін після деплою стає в чергу за cron, а не
вбиває його). *Чому :17, а не :00:* GitHub затримує або губить cron-задачі на початку години.
*Чому одне issue:* серія падінь за ніч дає одне сповіщення і коментарі з посиланнями, а не
десяток issues. *Чому звіт лише при падінні:* 8 зелених прогонів на добу дали б 8 артефактів,
які ніхто не відкриє.

**Що таке `@prod-safe`.** Тест не створює акаунтів і не пише нічого, що бачать люди або адмін:
health, `/ping`, каталог, «питання без відповідей», SEO і пререндер (`api/seo.spec.ts`),
лідерборд без id та email, пошук KB, `quiz/check` гостем, гостьова навігація, deep link з reload,
`/en`. Ніколи на проді: реєстрація, вхід, чат, коментарі, голоси, фідбек, баг-репорти (йдуть у
Telegram адміну), імпорт, відповіді в UI-квізі.
*Чому `quiz/check` можна, а UI-квіз ні:* гостьова перевірка рахує статистику «N% відповіли
правильно» лише з `first: true` у тілі. `ApiClient` його не шле, а UI на першу відповідь шле
(`$APP_DIR/apps/api/src/routes/quiz.ts`).
*Чому два запобіжники:* `grep` у конфігу пускає на прод лише `@prod-safe`, а фікстури `user` і
`newCredentials` падають на проді. Хибно позначений тест упаде, але акаунта не створить.
Umami під Playwright не шле нічого двічі: апка вимикає себе при `navigator.webdriver`, а фікстура
`context` ставить `umami.disabled`.

*Чому `retries: 1` тільки в CI:* одна повторна спроба відділяє інфраструктурний збій від баґу.
Тест, який пройшов з другої спроби, позначається як flaky, і його треба розібрати, а не терпіти.

## 4. Агенти: як фреймворк росте

Згенеровані `npx playwright init-agents --loop=claude`. Працюють через MCP-сервер
`playwright-test` (`.mcp.json`), який дає їм браузер і раннер тестів.

| Агент | Вхід | Вихід |
|---|---|---|
| `playwright-test-planner` | фіча апки + `tests/seed.spec.ts` | план сценаріїв у `specs/*.md` |
| `playwright-test-generator` | пункт плану | `.spec.ts`, перевірений у живому браузері |
| `playwright-test-healer` | червоний тест | діагноз і виправлення |
| `test-reviewer` (наш) | diff | список порушень правил фреймворку + `check` і `--repeat-each=3` |

**Нова фіча:** беремо фазу з [specs/COVERAGE.md](../specs/COVERAGE.md) (матриця вимог REQ-* → тести, гепи, пріоритети) → planner → (ти читаєш план) → generator → test-reviewer → виправлення → тег `@REQ-*` і статус у матриці (`npm run coverage` перевіряє, що вони сходяться) → commit.

**Червоний тест:** healer → test-reviewer.

Межа відповідальності healer: він може виправити локатор чи очікування, але якщо його фікс
змінює те, *що* перевіряє тест, це вже рішення людини. Це може бути справжній баґ апки, і тоді
healer його «вилікував» би.

*Чому seed з нашими фікстурами:* агенти стартують із seed. З голою `page` вони бачили б focus
wizard замість апки й генерували б тести під нього.

**`/ub-mode`** (скіл Uncle Bob, `.claude/skills/ub-mode`): дисципліна змін. Спершу зроби, щоб
працювало (найменша правка, TDD, межі й типи), потім зроби правильно (корінь проблеми, тест
поведінки, рефакторинг під захистом тестів), потім практика (малі коміти з «чому»). Вмикається
командою, на всю сесію. Відмінності від проєкту (PR замість push у `main`, без Crapper/Dryer/
Mutator) записані в CLAUDE.md.
*Чому копія, а не посилання:* скіл виконується в кожній сесії, тому його текст має бути
перевірений і зафіксований на коміті; оновлення — свідомий diff у PR.

**Бюджет контексту:** один чат до 150k токенів. Hook `.claude/hooks/context-guard.mjs` з 120k
просить закінчити крок, записати `.claude/handoff.md` і перейти в новий чат; новий чат стартує
з цього файлу.
*Чому:* у довгому чаті модель гірше тримає ранні рішення, а кожна відповідь дорожча. Handoff
переносить лише те, чого ще немає в git, документах і пам'яті.

*Чому правила в CLAUDE.md і test-reviewer, а не в файлах агентів:* повторний `init-agents`
перезаписує файли агентів.

## 5. Приклад root cause analysis (2026-10-28)

Симптом: 23 UI-тести червоні на всіх в'юпортах, API зелені. Кроки розбору:

1. **Спільне в падіннях.** Падають тільки UI-тести, і всі на першому ж локаторі оболонки
   (`dash`, `sidebar`). Отже, причина одна, і вона до самого сценарію.
2. **`error-context.md`.** У ARIA-знімку сторінки замість дашборду візард «Який твій напрям?».
3. **Документація апки** (`$APP_DIR/docs/test-ids.md`, «Focus wizard»). Новий відвідувач без
   `qa-hub-focus` отримує візард замість оболонки. Код: `lib/focus.ts`, значення `'skipped'`.
4. **Фікс в одному місці.** Фікстура `context` ставить `qa-hub-focus=skipped`. Заодно
   прибрано мертвий ключ `qa-hub-tutorial-offer`, бо апка його більше не читає.
5. **Перевірка.** Повний прогін, UI-набір з `--repeat-each=3`, `npm run check`.
6. **Системний висновок.** CI не запускався, коли змінювалась апка. Тому додано нічний
   запуск і `repository_dispatch`.
