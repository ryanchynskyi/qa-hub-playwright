# Модуль 5. Дизайн тестів і боротьба з флакі

**Після модуля ти можеш:** писати тести, що чекають на стан, а не на час, перевіряти бізнес-правила
з побічними ефектами (XP, щоденні задачі) відносно, робити недетермінований UI детермінованим і
доводити стабільність прогоном.

Файли: [tests/e2e/quiz.spec.ts](../../tests/e2e/quiz.spec.ts) ·
[tests/e2e/kb.spec.ts](../../tests/e2e/kb.spec.ts) · [eslint.config.js](../../eslint.config.js)

## 1. Чекати на стан, не на час

| Замість | Пишемо | Чому |
|---|---|---|
| `waitForTimeout(1000)` | `await expect(verdict).toBeVisible()` | або занадто довго, або замало на повільному CI |
| `expect(await x.isVisible()).toBe(true)` | `await expect(x).toBeVisible()` | перше перевіряє один момент, друге ретраїть до таймауту |
| `waitForLoadState('networkidle')` | assertion на потрібний елемент | застосунок опитує чат кожні 5 с, «тиші» може не бути |
| `if (await x.count())` у тесті | метод page object або явний `test.skip` | тест з гілками перевіряє різне на різних прогонах |

Більшість цих правил **зашито в лінт** (`no-wait-for-timeout`, `prefer-web-first-assertions`,
`no-networkidle`, `no-conditional-in-test`, `no-raw-locators`). `npm run lint` з
`--max-warnings=0` не пропустить їх у коміт. Правило в лінті надійніше за правило в голові.

### `expect.poll` для значень, яких немає в DOM-assertions

```ts
await expect.poll(() => shell.totalXp()).toBeGreaterThanOrEqual(before + 2);
```

XP оновлюється асинхронно після відповіді сервера. `expect.poll` повторює функцію, поки умова не
виконається або не мине таймаут. Це web-first підхід для довільних значень.

### Debounce без сну

Пошук у базі знань стартує від 2 символів з затримкою 250 мс. Тест не спить 300 мс: він перевіряє,
що після 1 символу результатів немає (`toHaveCount(0)`), а після `join` вони з'являються
(`toBeVisible()` з автоочікуванням).

## 2. Відносні assertions для побічних ефектів

Квіз 10/10 дає бонус 20. Але в прогоні з дослідження застосунку `quiz-result-bonus` показав
**60**, а загальний XP 165 при сумі відповідей 65. Щоденні задачі («дай N відповідей») теж
закриваються під час квізу і додають свої нагороди. Точне `toBe(85)` було б флакі залежно від
того, які задачі випали сьогодні. Тому:

```ts
expect(bonus).toBeGreaterThanOrEqual(20);
await expect.poll(() => shell.totalXp()).toBeGreaterThanOrEqual(xpBefore + shownGains + bonus);
```

Правило: **перевіряй інваріант, а не випадкове число**. Інваріант тут такий: «XP виріс принаймні
на те, що застосунок показав користувачу».

## 3. Детермінізм там, де UI випадковий

Порядок варіантів перемішаний, питання обираються з пулу. Щоб відповісти **правильно навмисно**,
`answerCorrectly` питає API: `POST /quiz/check` без токена з `choice: null` повертає
`correctIndex` і нічого не записує. Потім тест клікає `quiz-option[data-key=<index>]`. `data-key`
— це індекс у збереженому списку, а не позиція на екрані.

Це загальний прийом: **готуй або дізнавайся стан через API, перевіряй через UI**.

## 4. Ізоляція і паралельність

- `fullyParallel: true`: тести одного файлу теж ідуть паралельно. Це працює лише тому, що жоден
  тест не ділить змінюваних даних з іншим: свій гість (чистий контекст), свій `user`.
- Email з `randomUUID()`, а не з `Date.now()`: два воркери в одну мілісекунду дали б однаковий
  час.
- `--repeat-each=5 --workers=4` при побудові фреймворку: 280/280 зелені. Це і є доказ
  стабільності, а не «у мене один раз пройшло».

## 5. Тест, що нічого не перевіряє

Найнебезпечніший тест — зелений, але порожній:
- пропущений `await` перед `expect(...)` (ловить `no-floating-promises` + `missing-playwright-await`);
- цикл по порожньому масиву (`leaderboard`: `expect(top.length).toBeGreaterThan(0)` перед циклом);
- assertion на розпарсеному zod-об'єкті, з якого вже викинули поле (модуль 4);
- `Number(null) === 0` (тому `numberValue` падає на не-числі).

## Експеримент (15 хв)

1. Заміни у `kb.spec.ts` `expect.poll(...)` на `expect(await shell.totalXp()).toBeGreaterThanOrEqual(...)`
   і запусти `--repeat-each=10`. Чи завжди падає? Чому «іноді» гірше, ніж «завжди»?
2. Заміни `toBeGreaterThanOrEqual` у квізі на точне `toBe(xpBefore + shownGains + bonus)`.
   Запусти кілька разів, у тому числі після `npm run stack:reset`.
3. `npx playwright test tests/e2e --repeat-each=5 --workers=8`: що відбувається на межі
   ресурсів машини?

## Практика (1–1.5 год)

**Завдання A. Чат двох користувачів.** Хуки: `chat`, `chat-input`, `chat-send`, `chat-message`
(key = id, state `mine|other|deleted`), `chat-delete` (state `idle|confirm`), `chat-guest-cta`.
- [ ] Два користувачі в **двох контекстах** (`browser.newContext()` + власна фікстура або
      хелпер). A пише унікальне повідомлення, B бачить його зі state `other` (опитування раз на
      5 с: чекай на стан, не на час).
- [ ] A видаляє повідомлення двома кліками (`idle` → `confirm` → видалено), B бачить `deleted`.
- [ ] Гість бачить `chat-guest-cta`, а не поле вводу.
- [ ] `@local-only` (пише в БД). Подумай, що станеться при `--repeat-each=5` з лімітом
      «5 повідомлень на 30 с».

**Завдання B. Щоденні задачі.** `today` (v done, t total), `task` (state
`pending|running|done`, `data-type`).
- [ ] Залогінений користувач з 3 задачами за замовчуванням: `today` має `data-total="3"`.
- [ ] Виконай задачу типу ANSWER_N через квіз і перевір, що її state став `done`, а XP виріс
      принаймні на `data-reward`.
