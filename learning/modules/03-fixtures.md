# Модуль 3. Фікстури: стан браузера, дані, ізоляція

**Після модуля ти можеш:** пояснити життєвий цикл фікстури, обрати scope (test чи worker),
зробити опцію, яку перевизначає проєкт або файл, і побудувати ізольовані тестові дані з
прибиранням.

Файл: [src/fixtures/index.ts](../../src/fixtures/index.ts)

## 1. Анатомія фікстури

```ts
user: async ({ api }, use) => {
  // setup: виконується перед тестом
  const { accessToken, user } = await api.register({...});
  await use({ ...credentials, token: accessToken });   // ← тут виконується тест
  // teardown: виконується після тесту, навіть якщо він впав
  await deleteAccountIfExists(api, credentials);
},
```

- Фікстура **лінива**: створюється, лише якщо тест (або інша фікстура) її запросив. Тест без
  `user` не реєструє акаунт.
- Залежності в першому аргументі (`{ api }`) утворюють граф. Playwright сам вирішує порядок
  створення і зворотний порядок прибирання.
- Teardown після `use` виконується і для впалих тестів. Це надійніше за `afterEach`, який
  легко забути або зламати.

## 2. Що де в нашому файлі

| Фікстура | Scope | Навіщо |
|---|---|---|
| `lang`, `device` | test, **option** | значення за замовчуванням, які перевизначає проєкт (`use: { device }`) або файл (`test.use({ lang: 'en' })`) |
| `context` (override) | test | `addInitScript` до коду застосунку: вимкнена аналітика, без tutorial-offer, обрана мова |
| `api` | test | `ApiClient` на власному `APIRequestContext` з `baseURL = apiURL` |
| `catalog` | **worker** | `GET /content/catalog` один раз на воркер: ids для data-driven тестів |
| `user` | test | новий акаунт через API, видалення в teardown |
| `newCredentials` | test | незайняті креденшели для UI-реєстрації; прибирає акаунт, якщо його створили |
| `authedPage` | test | `page`, залогінена як `user` |
| `shell`, `quiz`, ... | test | page objects, створені з потрібним `page`/`device` |

### Чому `context`, а не `page`

`context.addInitScript` діє на **кожну** сторінку контексту, включно з новими вкладками і
попапами. `page.addInitScript` — лише на одну. Перевизначаючи вбудовану фікстуру `context`, ми
не міняємо жодного тесту: усі автоматично отримують чистий стан.

### Чому init script, а не `localStorage.setItem` після `goto`

Застосунок читає `qa-hub-lang` і `qa-hub-tutorial-offer` **під час старту**. Якщо записати їх
після `goto`, застосунок вже стартував українською, і оверлей вже на екрані. `addInitScript`
виконується до будь-якого скрипта сторінки при кожній навігації.

### Чому `catalog` worker-scoped, а `user` ні

Каталог лише читається і однаковий для всіх, тож кешувати його на воркер безпечно і дешево.
Користувач **змінюваний**: тест може набрати XP, змінити пароль або видалити акаунт. Спільний
користувач між тестами — класичне джерело флакі, що залежить від порядку запуску. Тому кожен тест
отримує свого.

## 3. `authedPage`: логін без UI

```ts
const res = await page.request.post(`${env.apiURL}auth/login`, { data: {...} });
await page.goto('dash');
await shell.expectSignedIn(user.email);
```

- `page.request` ділить cookie jar з контекстом браузера. Відповідь логіна ставить httpOnly-cookie
  `qa_rt` прямо в цей контекст. Застосунок при старті робить `POST /auth/refresh` з цією cookie і
  відновлює сесію.
- Логін через UI тестуємо **один раз** окремим тестом (`auth.spec.ts`). Решті тестів UI-логін
  лише додає секунди і точки відмови.

### Чому не `storageState`, як у документації

Стандартний рецепт «залогінься раз у global setup, збережи `storageState`, перевикористай»
тут **ламається**: refresh-токени ротуються при кожному використанні. Перший тест оновить токен,
решта прийдуть зі старим. Сервер вважає повторне використання крадіжкою і **відкликає всю родину
сесій** (docs/brief.md §7). Наш варіант (свій користувач і свій логін на тест) коштує ~100 мс на
тест і повністю ізольований. Це гарна відповідь на співбесіді на питання «чому ви не
використовуєте storageState?».

## 4. Прибирання, яке не ламає звіт

`deleteAccountIfExists` спочатку логіниться: якщо 401, акаунта вже немає (тест сам його видалив
або UI-реєстрація не відбулась), і прибирати нічого. Teardown не повинен падати там, де тест уже
впав з іншої причини: інакше в звіті дві помилки, і справжня ховається.

## Питання на співбесіді

1. Фікстури vs `beforeEach`: чим кращі фікстури?
2. Test-scoped vs worker-scoped: як обираєте? Наведіть приклад, коли worker-scope шкодить.
3. Як ви логінитесь у тестах? Чому не через UI? Коли `storageState` не підходить?
4. Як забезпечуєте ізоляцію тестових даних при паралельному запуску?
5. Що таке option-фікстура і як її перевизначити для одного файлу?
