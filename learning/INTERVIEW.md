# Питання для співбесіди з еталонними відповідями

Відповідай спершу сам (вголос або письмово), потім звіряй. Еталон спирається на код цього
фреймворку: на співбесіді найсильніша відповідь — «у моєму проєкті я зробив X, бо Y, альтернатива
Z не підійшла, бо…». Свої відповіді й оцінки ментора записуй у розділ «Мої відповіді» внизу.

## Модуль 1

**1. Як запобігаєте запуску деструктивних тестів на проді?**
Захист у коді, а не в дисципліні. Одне місце резолву середовища (`env.ts`): `TARGET` з білого
списку (`local|prod`, інше — помилка), для `local` будь-який не-localhost URL кидає помилку при
завантаженні конфігу. Для `prod` конфіг примусово фільтрує набір до `@prod-safe` у **кожному**
проєкті (project `grep` перекриває кореневий, тому фільтр будується в кожному) і не піднімає
`webServer`. Прод-набір лише читає дані.

**2. Навіщо проєкти? Як вирішуєте, що запускати на всіх в'юпортах?**
Проєкти ділять набір за середовищем виконання: API без браузера, UI на трьох в'юпортах. Бізнес-
логіка не залежить від розміру екрана, тому на tablet/phone йдуть лише `@responsive`-тести
(розкладка, навігація, smoke). Інакше час прогону ×3 без додаткового покриття.

**3. `globalSetup` vs `webServer` vs worker-фікстура?**
`webServer` запускає і чекає процес (наш стек) за URL. `globalSetup` — разова дія перед усім
прогоном у головному процесі (ми чекаємо `/health` з `db: up`, бо `webServer` перевіряє лише
web-порт, а прод засинає). Worker-фікстура — ресурс на кожен воркер, доступний тестам (у нас
`catalog`). Глобальна підготовка без потреби в даних у тестах — `globalSetup`; дані для тестів —
фікстура.

**4. `trace`: `on-first-retry` / `retain-on-failure` / `on`?**
`on-first-retry` записує лише при ретраї: дешево на CI, але локально з 0 ретраїв не записує нічого.
`retain-on-failure` записує все і зберігає лише впалі: повна картина першого ж падіння (у нас).
`on` — для дебагу конкретного тесту, на всьому наборі дорого.

**5. Чому `timezoneId` може врятувати від флакі?**
Логіка застосунку прив'язана до локальної півночі (щоденні задачі, стріки, «повторна відповідь
раз на день»). CI зазвичай в UTC, розробник у Києві: тест біля півночі поводиться по-різному.
Фіксована зона робить «сьогодні» однаковим скрізь.

## Модуль 2

**1. Стратегія локаторів?**
Тестові атрибути як контракт з розробкою: `data-testid` для елемента, `data-key` для ідентичності
в списках, ARIA або `data-state` для стану, `data-value` для чисел. Застосунок двомовний, тож
текст і ролі з accessible name нестабільні; CSS ламається від рефакторингу. Якщо test id немає:
попросити додати (це дешево), тимчасово `getByRole` з ім'ям у тесті з закріпленою мовою. Правило
підкріплене лінтом (`no-raw-locators` у specs).

**2. Що має і чого не має бути в Page Object?**
Має: локатори, дії мовою користувача, які самі чекають на результат (`answer()` чекає вердикт),
технічні перевірки стану сторінки (`expect*()`). Не має: бізнес-assertions сценарію, знання про
тестові дані, `if` за результатами тесту. Інакше page object не перевикористати в негативних
кейсах і помилка показує на page object, а не на вимогу.

**3. `BasePage` чи композиція?**
`BasePage` швидко стає звалищем (`goto`, хедер, футер, утиліти), і всі сторінки тягнуть усе.
Композиція: Shell — окремий компонент, сторінки маленькі, тест через фікстури отримує лише
потрібне. Успадкування доречне для справді спільної поведінки (базовий модальний діалог).

**4. Desktop і mobile без дублювання?**
Опція `device` з проєкту → компонент `Shell` ховає різницю (`open('chat')` на телефоні спершу
відкриває шторку). Тести однакові для всіх в'юпортів; специфічні перевірки розкладки зібрані в
`expectLayout()`. Тести лише для одного пристрою — явний `test.skip(умова, причина)`.

**5. Чому `if` у тесті — поганий знак?**
Тест з гілками перевіряє різні речі на різних прогонах: зелений результат не каже, яка гілка
виконалась. Зазвичай це ознака недетермінованого стану (його треба зафіксувати) або логіки, що
належить page object.

## Модуль 3

**1. Фікстури vs `beforeEach`?**
Ліниві (створюються лише на запит), композиційні (граф залежностей), з гарантованим teardown після
`use` навіть при падінні, з scope (test/worker), перевизначувані опціями. `beforeEach` виконується
для всіх тестів блоку, і стан передається через змінні в замиканні.

**2. Test vs worker scope?**
Worker — для дорогих і незмінних ресурсів (каталог, клієнт до БД). Test — для всього, що тест може
змінити. Шкідливий приклад: спільний користувач на воркер. Один тест набирає XP або змінює пароль,
і результат іншого залежить від порядку запуску.

**3. Як логінитесь? Чому не UI? Коли `storageState` не підходить?**
Логін через UI — один окремий тест. Решта логіняться через API в контексті тесту
(`page.request.post` ставить httpOnly-cookie в той самий cookie jar). `storageState` не підходить,
коли refresh-токен ротується: спільний збережений стан після першого використання стає
недійсним, а повторне використання відкликає всю родину сесій. Тож у нас свій користувач і свій
логін на тест.

**4. Ізоляція даних при паралельності?**
Кожен тест створює свої дані (`user` з UUID-email) і прибирає в teardown; гість — чистий
контекст. Нічого спільного змінюваного між тестами, тому `fullyParallel: true`. Читаємо лише
незмінне спільне (каталог).

**5. Option-фікстура?**
Фікстура зі значенням за замовчуванням (`lang: ['uk', { option: true }]`), яку перевизначає
проєкт (`use: { device: 'phone' }`) або файл/describe (`test.use({ lang: 'en' })`). Інші фікстури
від неї залежать (init script пише мову).

## Модуль 4

**1. API-клієнт?**
Обгортка над `APIRequestContext` (baseURL, cookies, trace безкоштовно). Типізовані методи для
happy path: перевіряють статус з інформативним повідомленням і парсять схемою. `raw` для
негативних кейсів. Тести не знають URL і форм тіла, лише методи.

**2. Контракт: схема vs `toEqual` з еталоном?**
Еталонний JSON ламається від будь-якої зміни даних (контент, час, id). Схема перевіряє форму і
типи (`status: 'ok'`, числа > 0, enum рівнів) і дає TS-тип через `z.infer`: одне джерело правди
для перевірки і коду.

**3. Strict чи non-strict?**
Non-strict пропускає нові поля: зворотно сумісні зміни API не ламають набір, але й витік поля
непомітний (zod його ще й викине). Strict ловить будь-яке нове поле і ламається від кожного
доповнення API. Компроміс: загальні схеми non-strict, а заборони («немає `correctIndex`») — явні
тести на сирому JSON.

**4. Security на рівні API?**
Відсутність секретів у відповідях (відповіді на тести), відсутність PII в публічних ендпоінтах
(id, email у рейтингу), однакові помилки для неіснуючого email і невірного пароля (enumeration),
`HttpOnly` на сесійних cookie, 401 без токена, CSRF/Origin-перевірка, валідація меж (400 замість
500).

**5. Параметризація; `test.step` + `expect.soft`?**
Масив кейсів + `for` навколо `test(...)`: кожен кейс — окремий тест з назвою в звіті. `test.step` +
`expect.soft` усередині одного тесту — коли набір кейсів відомий лише в рантаймі (секції з
каталогу) або треба побачити всі розбіжності одразу.

## Модуль 5

**1. Flaky: причини і ліки?**
(1) Чекання на час замість стану → web-first assertions, `expect.poll`. (2) Спільні дані між
тестами → свої дані на тест. (3) Точні значення з побічними ефектами → відносні інваріанти.
(4) Випадковість UI → дізнатись стан через API (`correctIndex`), брати за `data-key`. (5) Час і
таймзона → `timezoneId`. (6) Анімації і оверлеї → init-прапорці, чекати на стан після дії.
(7) Ресурси машини → обмежити воркери на CI.

**2. Web-first і auto-waiting?**
Дії (`click`, `fill`) чекають, поки елемент буде attached, visible, stable, enabled і отримує
події. `expect(locator)` ретраїть перевірку до таймауту. `expect(await locator.isVisible())`
перевіряє один момент і не ретраїть.

**3. Асинхронні значення з побічними ефектами?**
`expect.poll(() => readValue())` + інваріант замість точного числа: «XP ≥ до + показані
нагороди», бо щоденні задачі можуть додати своє.

**4. Детермінізм при випадковому UI?**
Вибір за стабільним ідентифікатором (`data-key` = індекс у збереженому списку), а правильну
відповідь беремо з API без побічних ефектів. Загально: готуємо або дізнаємось стан через API,
перевіряємо через UI.

**5. Як доводите стабільність?**
`--repeat-each=N` з кількома воркерами на новому і зміненому тесті (у нас 280/280 при 5
повторах), ретраї на CI з видимими flaky-мітками, жодних ретраїв локально.

## Модуль 6

**1. CI для e2e?**
Дешеві перевірки першими (typecheck, lint), потім браузери і тести. Застосунок з БД піднімається
в тому самому раннері (service container + `webServer`). Звіт і trace — артефакти навіть при
падінні. Прод-смоук — окрема джоба, вручну або за розкладом.

**2. Приватний застосунок + БД?**
Другий `actions/checkout` з fine-grained токеном (Contents: read), `npm ci` в обох, Postgres як
service; стек-скрипт приймає зовнішній `DB_URL`, API мігрує і сідить БД сам.

**3. Політика ретраїв?**
0 локально, 1 на CI. Ретрай не лікує флакі, він робить його видимим (мітка flaky) без блокування
мержу. Флакі-тест — баг з власником і терміном.

**4. Падає лише на CI?**
Trace з артефакту (DOM, мережа, консоль), `error-context.md`, порівняння середовищ (таймзона,
швидкість, воркери, дані в БД), відтворення з `--workers` як на CI і `--repeat-each`.

**5. 40 → 10 хвилин?**
`fullyParallel`, шардинг на кілька машин + `merge-reports`, підготовка даних через API замість UI,
логін через API, не ганяти бізнес-логіку на всіх в'юпортах, кеш браузерів і `node_modules`,
прибрати дублікати між API- і UI-рівнями.
