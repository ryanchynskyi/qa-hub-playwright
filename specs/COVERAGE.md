# Покриття вимог

Матриця трасування «вимога → тест» за документом «QA Interview Hub — вимоги до продукту»
(стан продакшну на PR #87, 2026-10-28), доповнена 2026-11-20 вимогами з чекліста апки на
`b824baf` (курси CRS, співбесіда і план PLAN, лендинг GEN-16, QUIZ-20, ADM-07…10, NFR-13).
Детальні перевірки до кожної вимоги — у `$APP_DIR/docs/regression-checklist.md` (ID виду
`QUIZ-007`, пріоритети P1–P3). Апка перенумеровує ID чекліста (QUIZ-030/031 → 053/054,
CRS-028/029 → 030/031, LB-004 → LB-008), тож теги тестів — лише за REQ.

Статуси: ✅ покрито · 🟡 частково · ❌ немає · ⛔ поза межами e2e (причина в примітці).
Шар для гепу: **API** (дешево, стабільно) або **UI** (лише те, що видно тільки в браузері).

### Трек I. Запуск: CI, nightly з Allure, prod smoke

Іде паралельно з фазами 0–3. Усе розкладене працює в GitHub Actions: репо публічне, тож хвилини

| Шар                 | Апка               | Набір                                  | Коли                               | Навіщо                              |
| ------------------- | ------------------ | -------------------------------------- | ---------------------------------- | ----------------------------------- |

2. Запушити гілку, відкрити PR, отримати перший зелений прогін `e2e.yml`, змерджити.

Готово, коли: зелений прогін в Actions на `main`.

#### I-1. PR gate і повний набір

1. ⏸ (відкладено, поки набір ~1,5 хв: один job `e2e` і є gate) Розділити `e2e.yml` на job `gate` (PR) і `full` (push, schedule, dispatch). Повний набір у PR —
   лише за міткою `full-e2e`.
2. ✅ Branch protection на `main`: `e2e` обов'язковий, і для адмінів теж (2026-10-28).
3. ✅ `concurrency` з `cancel-in-progress` для того самого ref.

#### II-4. Автоматичні gate ✅ (гілка `phase2-gates`, `npm run gate`)

Людина лишається там, де потрібне судження: план, зміна assert, правило, злиття.

| Gate         | Зараз                       | Після                                                                               |
| ------------ | --------------------------- | ----------------------------------------------------------------------------------- |
| План         | людина                      | людина                                                                              |
| Тест готовий | людина читає звіт           | reviewer `ready` + `--repeat-each=3` + mutation score ≥ поріг → PR ready for review |
| Фікс healer  | людина                      | автоматично, якщо assert не змінено; інакше рішення людини                          |
| Нове правило | людина                      | людина (кандидата пропонує головна сесія з журналу)                                 |
| Злиття       | людина після зеленого `e2e` | людина                                                                              |

Пороги беруться з даних II-2 і уточнюються петлею II-1: тест з `ready` потім червоніє або мутант
його проходить → поріг підняти.

Поріг mutation score: 100%, бо всі п'ять мутантів, що вижили в II-2, були справжніми прогалинами.
Вимога без мутанта теж не проходить. Цей gate також перевіряє повторюваний `weak-assert` generator
з II-3, який урок не зупинив: PROG-02/03 і SOC-01/02 мутантів ще не мають, тож зміна їхніх спек
спершу вимагатиме патчів. CI gate не запускає (мутант будує апку на кожен прогін), тож його
запуск, як і вердикт reviewer, лишається за головною сесією.

Готово, коли: людина бере участь лише в плані, рішеннях про assert і правила та злитті.

- **AUTH-09, «скидання пароля неверифікованого акаунта»:** такої сторінки й ендпоінта в апці

- **AUTH-18, регістр email:** чекліст PROF-012 каже «точно як email»; апка порівнює без регістру.
  Рішення: так задумано (email всюди без регістру), тест це перевіряє.
- **AUTH-06, fallback `qa-hub-rt`:** з постійною cookie рестарт переживається і без
  `qa-hub-rt`, тож гілку «cookie стерто, токен з localStorage» (AUTH-008 у чеклісті) перевіряє
  окремий тест. Рестарт браузера змодельовано новим контекстом без сесійних cookie

- **Результати квізу, `quiz-result-failed`:** рядок для скрінрідера рахував пропущене як failed, а
  шкала `fail` — ні. Власник апки виправив: `failed` дорівнює шкалі `fail`, пропущені йдуть у
  `quiz-result-skipped`, а `passed + failed + skipped = total`. Тест це перевіряє.

  TTL не задокументовано; не тестуємо.
- **AUTH-11, відхилений Google-потік:** callback прив'язує неверифікований акаунт і стирає його
  пароль ще до перевірки nonce. Тобто потік, завершений в іншій вкладці (`google_state`), усе одно
  забирає пароль. Тест 4.2 тому бере нову пошту і побічних ефектів не перевіряє. Закрито сесією
  апки 2026-11-02: порядок кроків ніхто не обирав свідомо, але захоплення акаунта нема; це
  стосується всіх парольних акаунтів, а відхилений потік для нового email створює акаунт.
