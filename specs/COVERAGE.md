## План

Порядок обрано за ризиком: безпека й цілісність XP, потім P1-сценарії з regression-checklist,
потім решта. У кожній фазі спершу йдуть API-тести, бо вони швидші й стабільніші. Кожну фазу
проганяємо так: planner (план у `specs/<фаза>.md`) → generator → `test-reviewer` → `--repeat-each=3`.

### Фаза 0. Інфраструктура (без неї решта не пишеться)

1. ✅ **Трасування.** Тег `@REQ-<розділ>-<nn>` на тестах (`tag` у `test()`), а скрипт
   `npm run coverage` (`scripts/coverage.mjs`) з `playwright test --list` виводить «вимога →
   тести» і падає, якщо статус у матриці не сходиться з тегами (✅/🟡 без тестів, ❌ з тестами,
   тег без рядка в матриці). Статус ✅ чи 🟡 ставить людина. `--grep @REQ-AUTH` запускає розділ.
   Без REQ лишились 3 інфраструктурні тести (health, консистентність каталогу, 401 без токена).
2. ✅ **Опція `visitor: 'returning' | 'new'`** у фікстурі `context`. Зараз focus wizard і тур
   вимкнені для всіх, а GEN-10…15 потребують «нового» відвідувача. `test.use({ visitor: 'new' })`.
3. ✅ **Google і адмін:** хелпер входу через fake Google e2e-сервера; фікстура `adminPage`
   (`admin@example.test`). Вхід іде через API, без UI (`googleLogin` у `src/fixtures`).
4. ✅ **Збої мережі:** `breakApi` (`src/helpers/network.ts`) на `page.route`: затримка, 500, обрив.
   Перший споживач: QUIZ-11. Далі GEN-08, AUTH-05/12.
5. ⏭ **`ApiClient`:** refresh/logout, `/me/progress`, `/me/quiz/finish`, recall cards/rate,
   daily-count, чат, коментарі, фідбек, баг-репорти, admin, `/ping`, `/auth/providers`.
   Рішення користувача: методи пишемо разом із тестами, яким вони потрібні (фази 1–2).
6. ⏭ **Page objects:** FocusWizard, Tour, Recall, Profile, Leaderboard, Chat, CommentsSheet,
   FeedbackDialog, Admin, Stats. Так само: разом із тестами фази 2.
7. ✅ **Guard для test id:** `npm run check:ids` (`scripts/check-test-ids.mjs`) перевіряє, що
   кожен id з `src/` і `tests/` є в `$APP_DIR/docs/test-ids.md` (NFR-11). Ловить дрейф апки до
   прогону тестів. Перший запуск знайшов `dash-cta` (апка прибрала його 2026-10-13).

### Трек I. Запуск: CI, nightly з Allure, prod smoke

Іде паралельно з фазами 0–3. Усе розкладене працює в GitHub Actions: репо публічне, тож хвилини
й GitHub Pages безкоштовні, і результати бачать усі, а не лише одна машина. Docker — інструмент
для відтворення CI на локальній машині, не розклад.

#### I-0. Запустити CI вперше (блокер усього треку)

Зараз CI ще ні разу не запускався: в `origin/main` лише scaffold, секретів немає.

1. Fine-grained токен з Contents: read на `qa-interview-tests` → секрет `APP_REPO_TOKEN`.
2. Запушити гілку, відкрити PR, отримати перший зелений прогін `e2e.yml`, змерджити.

Готово, коли: зелений прогін в Actions на `main`.

#### I-1. PR gate і повний набір

1. ⏸ (відкладено, поки набір ~1,5 хв: один job `e2e` і є gate) Розділити `e2e.yml` на job `gate` (PR) і `full` (push, schedule, dispatch). Повний набір у PR —
   лише за міткою `full-e2e`.
2. ✅ Branch protection на `main`: `e2e` обов'язковий, і для адмінів теж (2026-10-28).
3. ✅ `concurrency` з `cancel-in-progress` для того самого ref.
4. ✅ Кеш браузерів за версією `@playwright/test`.
5. ✅ Input `app_ref` у `workflow_dispatch` (за замовчуванням `main`). SHA апки — в job summary.
6. Шардинг (`--shard` + blob + `merge-reports`), коли `full` перевищить ~10 хв.

Готово, коли: PR без зеленого `e2e` не мерджиться.

#### I-2. Nightly з Allure ✅ (крок 7)

Зроблено в `nightly.yml`; рішення 2026-10-28: випадковий лише браузер, api + усі три пристрої
на ньому; падіння лише в одному браузері — баг апки (issue). Деталі в `docs/WORKFLOW.md`.

1. `allure-playwright` поруч з HTML-репортером; Allure Report 3 (`allure` з npm, без Java).
2. Job `nightly`: matrix `app_ref: [main, develop]`, `--fail-on-flaky-tests`.
3. Звіт на GitHub Pages: окремий шлях на кожен `app_ref`. Історія переноситься між прогонами
   через `historyPath` (файл історії зберігається в гілці `gh-pages`). Це дає тренди, flaky і
   тривалість.
4. `allurerc.mjs`: environment (SHA апки, ref, ціль), categories (product bug / test defect /
   infra за текстом помилки).
5. Падіння nightly → issue (як у I-4).
6. **Випадковий браузер (запит користувача 2026-10-28).** Нічний прогін бере випадковий
   браузер (chromium / firefox / webkit), і api + усі три пристрої йдуть на ньому. Фабрика
   (`src/config/run-factory.ts`) з `SEED` вибирає браузер і будує `use` кожного UI-проєкту.
   `SEED` пишеться в лог, summary і Allure environment, падіння відтворюється через
   `SEED=<n>`. Без `SEED` усе як раніше (chromium).

Готово, коли: зранку за посиланням на Pages є звіт з трендом за кілька ночей для обох гілок.

#### I-3. Тригери з апки ✅ (крок 8, PR #18; апка `ee94caa`)

Прогін тестує `client_payload.sha` (точний коміт), гілка — у summary. Деталі в `docs/WORKFLOW.md`.

1. У workflow апки після push у `develop`/`main` і після деплою проду — крок
   `gh api repos/ryanchynskyi/qa-hub-playwright/dispatches -f event_type=<app-updated|prod-deployed>`
   з `client_payload` = ref і SHA.
2. Токен з правом на `qa-hub-playwright` (Contents: read and write) — секрет у репо апки.
3. У нас `app-updated` запускає `full` на `client_payload.ref`, а `prod-deployed` — prod smoke.

Готово, коли: коміт в апку запускає наш прогін з її SHA у звіті.

#### I-4. Prod smoke ✅ (PR #7, #8)

1. Розширити `@prod-safe` read-only перевірками:
   - `/health` і `/ping`;
   - консистентність каталогу;
   - **питання без відповідей** (NFR-03);
   - пререндер і SEO (GEN-07);
   - гостьова навігація з reload глибокого лінка (SHELL-016);
   - `/en`;
   - пошук бази знань;
   - лідерборд без id та email.
2. Перед тегуванням перевірити в коді апки:
   - `quiz/check` без токена не впливає на статистику «N% відповіли правильно» (QUIZ-09);
   - Umami нічого не шле з нашим init script (NFR-06).
3. Ніколи на проді: реєстрація, вхід, чат, коментарі, голоси, фідбек і баг-репорти (йдуть у
   Telegram адміну), імпорт.
4. Розклад: cron кожні 3 год + `prod-deployed`; `workers: 2`, `retries: 1`, timeout 10 хв.
5. Алерт: падіння відкриває або доповнює одне issue «Prod smoke failing» з посиланням на
   прогін (`permissions: issues: write`). Перший зелений прогін його закриває.

Готово, коли: падіння проду видно як issue протягом 3 год або одразу після деплою.

#### I-5. Docker для відтворення CI (за потреби)

Коли тест червоний лише в CI, або коли з'являться скриншот-тести (baseline тільки з Linux).

1. `npm run test:docker`: образ `mcr.microsoft.com/playwright:v<версія @playwright/test>-noble` +
   `postgres:17` у compose; `node_modules` апки в іменованому томі (Windows-збірка Prisma в Linux
   не працює); `DB_URL` на сервіс postgres.
2. CI-job `full` запускається в тому самому образі (`container:`), щоб середовища збігались.
3. Передумови: `wsl --install`, Docker Desktop, сховище Docker на D: до першого pull (на C:
   вільно 28 ГБ).

Готово, коли: CI-only падіння відтворюється однією командою локально.

### Поза e2e (рішення потрібні від апки)

- **Rate-ліміти** (AUTH-03, чат, коментарі, голоси, репорти): e2e-сервер їх вимикає.
  Варіанти: прапорець для окремого інстансу API або залишити це юніт-тестам апки.
- **Серверний час** (стрик акаунта, `tz_cooldown` 24 год, AUTH-17): потрібен тестовий хук
  годинника в e2e-сервері, інакше лише гостьовий рушій через `page.clock`.
- **Lighthouse** (NFR-08): окремий job з `@lhci/cli`.

## Неоднозначності у вимогах

- **Брейкпоінти:** KB-02 використовує ≤ 860 px, FB-01 ≤ 720 px. Наш tablet (800 px) для бази
  знань — «телефон», а для фідбеку — ні. Це варто зафіксувати в `Shell`/page object, а не в тестах.
- **Кількості контенту** («15 розділів» у QUIZ-01, «16 досягнень» у PROG-10, 871 питання тощо)
  змінюються разом із контентом. Тести беруть їх з `/content/catalog` чи `/health`, а не з вимог.
- **QUIZ-09, поріг:** чекліст QUIZ-036 каже «від 10 перших відповідей, менше 5 — немає»; апка
  (`QUESTION_STAT_MIN` = 5) і test-ids.md — від 5. Тести беруть константу; діапазон 5–9 у
  чеклісті не визначений.
- **ID у чеклісті переплутані:** бриф зводить QUIZ-19 до QUIZ-043, а QUIZ-14 до QUIZ-037; у
  regression-checklist.md навпаки (QUIZ-037 = коментарі, QUIZ-043 = результати). Теги — за REQ.
- **`quiz-result-row`:** `data-key` — id глави, але рядки групуються інакше, тож ключ не
  унікальний (два рядки `sq-1`). Тести лише сумують рядки.
- **test-ids.md пише `t = N`** для шкал і прогресу; реальний атрибут — `data-total`.
- **AUTH-17** прив'язана до дати 2026-10-20. Без даних, створених до цієї дати, її не перевірити
  в чистій БД.
- **Імпорт, PROG-14 в UI:** після «Перенести» апка очищує гостьове сховище, тож двічі імпортувати
  ті самі дані з UI неможливо. Тест повертає копію `qa-hub-guest-v1.imported` назад (як з іншого
  пристрою); строгу перевірку «0 XP, усі лічильники 0» робить API-тест.
- **Імпорт, джерело в банері:** ознаки джерела (гість / стара версія) з test id немає, тож тест
  звіряє текст «гостьовий режим»; мову фіксує фікстура `lang: 'uk'`.
- **Імпорт, «Нового нічого»:** повідомлення не містить «+0 XP»; «0 XP» перевіряємо через `xp-total`
  і API.
- **Імпорт, множина в uk:** банер і підсумок пишуть «1 відповідей» (баг апки,
  qa-interview-tests#90). Тести звіряють лише числа, не слова.
- **Імпорт, «сховище очищено» (IMP-004):** ключ `qa-hub-guest-v1` не видаляється, а замінюється
  порожнім станом; тест перевіряє, що `questions` і `cards` порожні.
- **Онбординг, кроки майстра:** у gate 5 кроків (manual) і 6 (auto), тема останній; чекліст DASH-027
  рахує «4 (5 після auto)» без теми. `focus-next` немає на кроках напряму й рівня (клік веде далі);
  `focus-setup` `data-state` після auto не відповідає номеру, тож тести звіряють `focus-step`.
- **Recall (прийнято, апка правильна):** лічильник «n / N», а не «Card n of N»; оцінка 1 вставляє
  картку на 3 позиції далі (один раз за сесію) і N росте на 1; інтервали 1/3/7/14 — це оцінки 2–5,
  оцінка 1 = та сама сесія; XP немає й тоді, коли картку вже оцінено сьогодні; порядок карток не
  фіксований, тести беруть `recall-card[data-key]`. Відповідь картки в API — markdown.
- **Онбординг, тема:** до вибору на `<html>` немає `data-theme` (системна тема), тож поточну тему
  тест читає з `focus-theme` `selected`.
- **Онбординг, тур:** у нового гостя 3 кроки (без `weak`); `weakHint` після «Готово» `false`, після
  skip/Escape `true` — тести перевіряють лише `stage: done`. Overlay `tour` для Playwright завжди
  «hidden» (видимий лише `tour-pop`), тож кінець туру — `toHaveCount(0)`.
